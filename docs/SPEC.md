## 1. Мета спільного проєкту

Реалізувати в одному репозиторії дві комплементарні утиліти, що ілюструють
ключові механізми Linux-програмування на рівні процесів:

- **minishell** (варіант 1) — інтерактивний інтерпретатор одиничних команд.
- **pipeline** (варіант 11) — виконавець конвеєра з кількох команд.

Разом вони формують функціональний прототип Unix-shell:
`minishell` парсить введення користувача та запускає одиничну команду;
`pipeline` бере рядок з `|` і запускає кілька процесів, з'єднуючи їх через
ядерні пайпи. Кожна частина здається індивідуально, але демо може бути
спільне.

## 2. Розподіл відповідальності

| Компонент | Відповідальний | Системні виклики |
|---|---|---|
| `minishell/` (REPL, парсер однієї команди, `exit`, перевірка помилок) | Артем | `fork`, `execvp`, `waitpid`, `perror` |
| `pipeline/` (парсер `\|`, N процесів, pipe-tree, dup2-роутинг, очікування) | Назар | `pipe`, `fork`, `dup2`, `execvp`, `waitpid`, `close` |
| Спільний build (`Makefile` верхнього рівня, README, інструкції) | Обидва | — |

## 3. Контракт інтерфейсу

Між двома частинами **немає прямого програмного зв'язку** —
це дві самостійні CLI-утиліти. Логічний зв'язок проявляється тільки
у спільному демо:

```bash
./minishell/minishell             # запускає REPL
> ./pipeline "ls | wc -l"         # викликає pipeline як зовнішню команду
```

Такий дизайн є навмисним: він зберігає Unix-філософію
(*do one thing well, compose via processes*) та дозволяє кожному
автору пояснювати власний код незалежно.

## 4. Pipeline (варіант 11) — короткий опис

**Вхід:** єдиний аргумент командного рядка — рядок з командами через `|`.

**Вихід:** stdout/stderr виконаних команд + повідомлення про exit-коди
кожного процесу у stderr; код повернення дорівнює exit-коду останньої
команди (як у bash).

**Алгоритм:**

1. Розбити вхід за `|` → масив `cmd_strs[N]`.
2. Для кожної `cmd_strs[i]` розбити за пробілами → `argvs[i]`.
3. Створити `N - 1` пайпів: `pipes[N-1][2]`.
4. У циклі `i = 0..N-1`: `fork()`.
   - У дитині `i`:
     - якщо `i > 0` → `dup2(pipes[i-1][0], STDIN)`;
     - якщо `i < N-1` → `dup2(pipes[i][1], STDOUT)`;
     - **закрити всі `pipes[*]`** після `dup2`;
     - `execvp(argvs[i][0], argvs[i])`.
5. У батьку: **закрити всі `pipes[*]`** (інакше деякі дитини зависнуть на `read`).
6. `waitpid(pids[i])` для кожного дитини; зібрати exit-коди.

**Граничні випадки:**

- N == 1 (без `|`) → один `fork()`, без `dup2`, без пайпів.
- Команда не знайдена → `execvp` повертає -1, дитина виходить з кодом 127.
- Користувач натиснув Ctrl-C → діти отримають `SIGINT`, parent відрепортить.

## 5. Minishell (варіант 1) — короткий опис *(виконує Артем)*

**Інтерактивний REPL:**

1. Вивід запрошення (`$ `).
2. Читання рядка через `fgets`.
3. Спецкоманди: `exit` → завершення REPL.
4. Інакше: `fork()` + `execvp()` + `waitpid()`.
5. Вивести exit-код виконаної команди.

## 6. Спільні вимоги до коду

- Стандарт: **C11**, флаги `-Wall -Wextra -O2`.
- Усі системні виклики перевіряються; помилки звітуються через `perror()`.
- Цільова платформа: Linux x86_64, glibc, ядро ≥ 5.x.
- Збірка через `make` (як в LR1–LR11 цього курсу).

## 7. Демонстраційні сценарії

| # | Команда | Що демонструє |
|---|---|---|
| 1 | `./pipeline "ls /usr/bin \| wc -l"` | Простий 2-pipe |
| 2 | `./pipeline "cat README.md \| grep pipe \| wc -l"` | 3-pipe з фільтром |
| 3 | `./pipeline "ps aux \| grep root \| sort -k1 \| head -5"` | 4-pipe |
| 4 | `./pipeline "cat nonexistent.file \| wc -l"` | Помилка у початковій команді |
| 5 | `./pipeline "ls \| nosuchcommand_xyz \| wc -l"` | Помилка `execvp` у середині |
| 6 | `./minishell` → `ls -la`, `pwd`, `exit` | REPL з одиничних команд |
| 7 | `./minishell` → `./pipeline "ls \| wc -l"` | minishell викликає pipeline |

## 9. Що не входить у scope

- Підтримка `>`, `<`, `>>` редиректів (опціонально, може бути додано після
  основного дедлайну).
- Builtin-команди типу `cd` (у minishell — лише `exit`).
- Job control (`&`, `jobs`, `kill %N`) — окремий варіант 2.
- Мережеві канали (`socketpair`) — не передбачено методичкою.
